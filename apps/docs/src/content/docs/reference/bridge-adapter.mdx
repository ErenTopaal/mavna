Every rail is one of these and nothing else. Adding a rail must require zero
changes outside its own package, which is why nothing in this interface names a
bridge, a chain, or an SDK.

Everything on this page is lifted from `packages/core/src/adapter.ts` when the
site is built, comments included. If it disagrees with the source, the source
moved and this page is a bug.

<Interface />

## `quote`

<Request />

Answering with a rejection is a normal outcome and is preferred to throwing,
because the reason gets shown to a person. Throw only for something a caller did
wrong.

Two obligations, both load-bearing:

**Resolve within the racing timeout.** `ADAPTER_QUOTE_TIMEOUT_MS` is 3000. One
slow rail must never hold up the others, and `raceAdapters` will drop you and
report `timed-out` in your name.

**Validate the destination yourself.** Nothing above the adapter knows what a
valid destination looks like on your chain. Stellar has several address forms
with different behaviour, some destinations silently swallow funds without a
memo, and a destination that cannot receive a given asset fails in ways that vary
by path. Never infer any of that from the shape of the string.

`maxSlippageBps` is the user's chosen bound. Unbounded slippage is not acceptable
on any path, so if your rail can deliver less than it quoted, `receivesAtLeast`
has to reflect this number.

## `buildTransactions`

<Transaction />

Build, never sign, never submit. `payload` is opaque to everything above you; the
caller's wallet is what knows how to read it.

`describes` is shown to a person before they approve it, so it is a sentence
about what will happen to their money and not a function name. The CCTP adapter
emits "Let Circle's transfer contract move 25 USDC from your wallet, once. This
does not send anything on its own."

`ephemeralSigners` stays empty on every chain that has no such concept. Solana's
burn writes its message into a brand new account, so one exists that is neither
the user nor anything derivable, and the caller has to generate a keypair and
sign with it. Carrying that here means a caller learns about it from the type
rather than from a failed signature. The SDK does not create the keypair, because
creating one means holding a secret key.

### Transactions that should not always be sent

<Unnecessary />

An ERC-20 approval is the case this exists for. The SDK cannot check an existing
allowance itself, because reading one needs a node on the source chain and the
caller is the one already holding a connected wallet. So the condition is stated
in a form the caller can evaluate, rather than the transaction being emitted
unconditionally and the wasted gas being someone else's problem.

Ask for exactly the amount being sent. An unlimited approval is a standing claim
on someone's funds that outlives the transaction they signed.

## `status`

Takes a handle, returns a `StepPhase`. The phases are described in
[core types](/reference/types/).

Two rules that are easy to get wrong:

**Never report failure without evidence.** A transfer that is merely not indexed
yet is `pending`. Reporting it as failed is how a user is talked into sending a
second payment.

**Do not conflate the rail with the destination.** On CCTP the attestation is the
authoritative signal for the cross-chain leg, and whether funds actually landed
is a fact on the destination chain. A completed attestation with nothing
delivered is exactly the case the status machine escalates from pending to
stalled, which is the whole reason that distinction exists.

## `recover`

Optional. A recoverable failure has to be recoverable from inside the product,
without the user needing a third-party explorer, documentation, or support.

## `TransferHandle`

<Handle />

All three keys are first class, and that is a deliberate departure from the prior
art, which resumes only from a transaction hash or an internal task id and whose
own type refuses a deposit address as a key. On Stellar a deposit address plus
memo is the natural shape, and a user who closed the tab has their destination
address if they have nothing else.

`sourceChainId` is optional for the same reason. An adapter that spans many
chains should search when it is absent rather than decline. The CCTP adapter
issues one lookup per source chain in parallel, which is 26 of them on testnet,
because that is a small price for not telling someone their transfer cannot be
found.

## What the routing layer does with all this

`raceAdapters` from `@mavna/routing` asks every adapter at once and returns a
`RouteSet` carrying routes and rejections together, with `complete` saying
whether everyone has answered. Pass `onUpdate` to render results as they land.

Partial results are the normal case here, not a degraded one, and an interface
built on this should look intentional while it is still filling in.
