You are building your own interface and want the routing, the quoting and the
transaction building. This gets you a real quote off the live network, then
explains the four decisions in it that are not obvious.

Read [what is published](/install/) first. The short version is that nothing is
on npm, so this walks the in-repository path.

## Run it

```sh
pnpm install
pnpm build
node apps/docs/examples/quote.ts GBD4SMJWOYPPTVSRUK7J5M3JHHOOIEUMWYGQOLHVHUDL4ZN2ESE3BJYA 25 ethereum-sepolia
```

Any Stellar address works, including one that does not exist yet. Node 24 runs
TypeScript directly, so there is no build step between the file and the output.

That command prints this, and every line of it came off the network:

```
layerzero declined (asset-unsupported): This route carries no token on the test network. It works on the main network, where it is the only way to bring USDT to Stellar. Another route may work here.
axelar declined (temporarily-unavailable): This route did not answer in time. Nothing has been sent, and it is worth trying again.
Route cctp-ethereum-sepolia-stellar via cctp
  sends     25.0 USDC
  receives  25.0 USDC
  at least  25.0 USDC
  takes     about 5 minutes
  signatures 3
  fee bridge: 0.0 USDC
  fee account-reserve: 1.5 XLM
  step prepare-account
  step approve-source
  step bridge
  step settle-account

2 transactions to sign, in this order:
  evm-tx on ethereum-sepolia: Let Circle's transfer contract move 25 USDC from your wallet, once. This does not send anything on its own.  (skippable, see unnecessaryWhen)
  evm-tx on ethereum-sepolia: Send 25 USDC to GBD4SMJWOYPPTVSRUK7J5M3JHHOOIEUMWYGQOLHVHUDL4ZN2ESE3BJYA on Stellar, via Circle, on the standard path.
```

Three rails were asked at once and one of them answered. That is the normal
result on testnet and the two refusals are worth reading rather than skipping:
LayerZero has no token to carry there at all, and Axelar did not come back inside
the three-second racing budget, which is what the budget is for. Neither is an
exception, an empty list, or a silent omission. Both are values in
`RouteSet.rejected` with a reason you can branch on and a sentence you can show.

The bridge fee is genuinely zero. Circle's standard path charges nothing into
Stellar, which is the whole commercial argument for building on it directly: a
reseller has to add their margin to zero and you can see that they did.

The 1.5 XLM is not a fee anyone takes. That address has no account on Stellar, so
one has to be created and given a trustline, and the XLM becomes a reserve locked
in the user's own account. If they ever close it, they get it back. Quote against
an address that already holds USDC and the line disappears.

## Four things in there that are not obvious

### The network is configuration, never a code path

`createNetworkConfig` is called with an explicit `id`. There is no testnet mode
anywhere in these packages and no default network, because a product that moves
money must never be ambiguous about which one it is on, and a default would
eventually be wrong in the expensive direction.

The mainnet case needs one more decision from you. The Stellar Development
Foundation runs no public mainnet RPC, so `PUBLIC_TESTNET_RPC_URL` has no mainnet
twin you can just swap in. `PUBLIC_MAINNET_RPC_URLS` carries three endpoints that
were measured rather than collected, ordered by latency, and you should point at
your own provider in production.

### `RpcClient` refuses stale answers, and that is why it retries

Stellar's public endpoint is load balanced across nodes that are not at the same
point in the chain's history. Ask twice and you can be told an account exists,
then that it does not, then that it does again.

`RpcClient` keeps a high-water mark of the highest ledger it has seen, rejects
any answer from behind it, and retries with backoff. So a call that takes a
second longer than you expected is the guard working, not the network being slow.
When it gives up it throws a `MavnaError` with `retryable: true`, which is a
different thing from the destination being unusable and must not be shown to a
user as though it were.

### An asset is a chain plus an identifier, never a symbol

```ts
const to: Asset = {
  chainId: "stellar-testnet",
  id: `USDC:${CCTP_CONTRACTS[NETWORK].usdcIssuer}`,
  symbol: "USDC",
  decimals: 7,
  curatedBy: "Circle",
};
```

Anyone can issue a Stellar asset with the code `USDC`. Identity is the code plus
the issuer, so `id` carries both, and on an EVM chain it is the token contract.
`symbol` is for display only and nothing decides anything from it.

Note the decimals: six on the EVM side, seven on Stellar. The adapter converts
between them in `BigInt`, and doing that arithmetic in `Number` is how a transfer
quietly loses its last digit.

### Amounts are integer strings, in base units, everywhere

`sends.baseUnits` is `"25000000"`, not `25`. Floating point on money is a defect
rather than a shortcut, and 7-decimal Stellar amounts exceed what a double
represents exactly, so this is not a theoretical concern. `amountOf` from
`@mavna/core` builds one and throws on anything that is not a non-negative
integer.

## What comes back when there is no route

A rejection, not an exception. `raceAdapters` returns a `RouteSet` carrying both:

```ts
const routes = await raceAdapters([cctp, axelar, layerzero], request);
for (const rejection of routes.rejected) {
  console.error(`${rejection.source}: ${rejection.explanation}`);
}
```

Every rejection carries a machine-readable `reason` and an `explanation` written
for a person. Two real ones, from the same file with a bad address and then with
half a dollar:

```
cctp declined (destination-unsupported): Not a Stellar address: NOTANADDRESS
cctp declined (amount-too-small): This transfer is too small to set up a new Stellar account. Send at least 6 XLM of value, or send to an address that already has one.
```

The second is the interesting one. It refuses and then says what would work,
which is the point of checking at quote time rather than after a signature.

`temporarily-unavailable` is the reason to handle deliberately, and it means two
different things depending on who said it. From CCTP it usually means the Stellar
read was too stale to trust, not that the address is bad. From the race itself it
means that rail did not answer inside `ADAPTER_QUOTE_TIMEOUT_MS`, which is 3000.
Neither is a verdict on the transfer, and showing either as a destination problem
tells a user their address is unusable when the truth is to ask again.

`RouteSet.complete` tells you whether every source has answered. Pass `onUpdate`
and render routes as they land rather than waiting for the slowest one:

```ts
await raceAdapters(adapters, request, { onUpdate: (partial) => render(partial) });
```

Partial results are the normal case here, not a degraded one, so an interface
built on this should look intentional while it is still filling in.

## Signing is yours, and there are more signatures than transactions

The quote above says three signatures and `buildTransactions` returned two. That
is not a bug and it is worth understanding before you build a flow around it.

The two are the EVM approval and the burn. The third is `prepare-account`, a
Stellar transaction that creates the destination account and its trustline, and
it has to land before the funds arrive: value arriving at an unprepared account
is rejected as a whole unit. It is built by `buildPreparation` in
`@mavna/stellar`, and it is sourced and paid for by a sponsor account, because
the arriving user by definition has no XLM to pay with.

`signaturesRequired` on the route counts every signature the whole transfer will
ask for, so you can tell the user upfront instead of surprising them one prompt
at a time. `buildTransactions` on the CCTP adapter returns only the source-chain
transactions.

**What is not wired up yet, stated plainly.** The sponsor service exists in
`services/sponsor` and the Stellar-side builders exist in `@mavna/stellar`, but
the reference app does not yet sign and submit the Stellar side. A destination
that already holds USDC needs none of that and reduces to the two EVM
transactions above. A destination that does not is quoted correctly and priced
correctly, and cannot yet be completed by this repository's own app.

Separately: no transfer has been signed and broadcast through a real wallet from
this codebase. Driving a wallet extension needs a browser with one installed and
that has not happened yet. Quoting, destination inspection and transaction
building are exercised against the live network; the signature at the end of it
is not, and this documentation will say so until it is.

## Sending from somewhere other than an EVM chain

Pass a different `chainId` and the quote works the same way. Both non-EVM
families were quoted while writing this page, from the same code:

```
solana-devnet    -> route, receives 250000000, sigs 2
starknet-sepolia -> route, receives 250000000, sigs 2
```

Two signatures rather than three, because neither chain makes the approval a
transaction of its own: Starknet folds it into the same invoke, and Solana's burn
is authorised by the owner who is already signing. `EVM_DEPLOYMENTS` and
`NON_EVM_CHAINS` are the two registries, and `supportedChains()` returns both.

Building for Solana needs one thing the route cannot carry:

```ts
const transactions = await cctp.buildTransactions(route, {
  solana: {
    owner: walletPublicKey,
    // A fresh keypair you generate and sign with. The burn writes its message
    // into that brand new account. The SDK will not create it, because creating
    // one means holding a secret key.
    messageSentEventData: messageAccount.publicKey,
  },
});
```

Leave it out and you get a `MavnaError` saying exactly that, rather than a
transaction that fails at signing time.

What comes back is one transaction in `solana-instruction` format, with
`ephemeralSigners` set to `["message_sent_event_data"]`. That is the role of the
account, not its address: it tells you which of the accounts you supplied has to
sign in addition to the wallet. On every EVM chain the same field is empty.
