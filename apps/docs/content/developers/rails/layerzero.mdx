# LayerZero OFT

`@mavna/adapter-layerzero`, id `layerzero`, trust model `dvn-stack`. A token that
implements LayerZero's Omnichain Fungible Token standard moves by message, and a
set of Decentralized Verifier Networks attests to that message. The token's owner
chose that set, so two routes on this same rail can be verified by entirely
different parties. It exists for one reason: it is the only route to native USDT on
Stellar.

```ts
const layerzero = new LayerZeroAdapter({ network, rpc, baseReserveStroops });
```

## Assets and chains

On mainnet, the adapter routes USDT0 from twelve candidate source chains. On the
test network, LayerZero's OFT registry carries no obtainable token, so a team that
has deployed its own OFT names it to the adapter and quotes over it. Each chain in
the list is only a candidate: every quote re-derives the endpoint, the OFT, the
peer, and the verifier set from the chain and declines when anything is missing.

`sendableAssets(chainId)` answers what a quote request should name, from the
deployment rather than from a symbol:

```ts
const { from, to } = await layerzero.sendableAssets("arbitrum");
// from.id: the token the chain's OFT moves, from its own token()
// to.id:   "USDT0:GATISXX6BZ6NC7IKQBY37CJD4SOZL3CYZJWXEDG6JVIY4WBS6KXJHN6Q"
```

The Stellar side is read from the token the Stellar OFT credits. When that token is
a Stellar asset contract, its `AssetInfo` storage gives the code and issuer, and the
adapter checks that this asset derives the contract's own address before using it.
Routes and delivered status are labelled with that classic asset. A token with no
code and issuer is refused by `sendableAssets` with the reason.

## Converting on arrival

Given an Arrival Contract, the adapter also quotes a compose route: the same send,
delivered to the [Mavna Arrival Contract](https://github.com/ErenTopaal/mavna/tree/main/contracts/arrival)
with a message saying who receives it, in which asset, and the least they accept.
LayerZero's executor then calls the contract, which converts through Aquarius on
Stellar and sends the wanted asset on.

```ts
const layerzero = new LayerZeroAdapter({
  network,
  rpc,
  baseReserveStroops,
  // the testnet deployment, also exported as ARRIVAL_CONTRACTS.testnet
  arrival: {
    contract: "CDAIQ522QK5AFCCVGENKVE7SDF6KRCDCAPRFGUWQ4GXO4NJZRVOHQN6X",
    venue: new AquariusProvider(network),
  },
});
```

The contract is deployed on testnet only; mainnet has none until it is
independently audited, and the rail says so rather than quoting a compose route
there. A compose route adds no step and no signature. It is declined, with the
reason, for a muxed address (the message carries a 32-byte recipient), a
recipient that cannot hold the wanted asset, a token or conversion path the
contract was not built to accept, and a wanted asset that is what arrives anyway.
A brand-new account is left to the plain route. The integrator fee, 0 to 1000
basis points, is taken only here, by the contract, from the converted amount.

If the conversion cannot meet the minimum, the arriving token is delivered as it
came, which status reports as `delivered-as-came`. A step LayerZero's executor
leaves unrun can be finished by anyone; [delivery](/developers/concepts/delivery)
covers how arrival is proven and what finishing takes.

## Who could lie to you

The verifier set is the answer to "who could lie to you," so the adapter refuses to
route through two kinds of set. It refuses a set with no required verifier, where
nothing would confirm the transfer, and it refuses a set nobody chose: an inherited
network default, because LayerZero can change who verifies a token's transfers
without the token's owner acting. Only the token owner's explicitly configured set
is accepted, and every send the adapter builds names the verifiers on it, by the
name LayerZero's DVN list gives each one for that chain, or by address where the
list has none (the list covers mainnet only, so on testnet every verifier is an
address). It says how many must agree and after how many source-chain
confirmations. That list is read with the rest of the deployment, so a quote
declines while it cannot be reached.

## Refusing a superseded deployment

Everything about the deployment is resolved and cross-examined at quote time,
because the recorded Stellar addresses were superseded while still live and
answering. The decisive check asks the Stellar OFT which endpoint it is registered
on and refuses to send if that differs from the registry's current endpoint, which
is what stops a transfer routing into a deployment that is no longer the advertised
one. The delivered decimals are required to be seven.

The Stellar side is checked in the other direction too, because a message it would
refuse is stranded after the source has already taken the funds. The Stellar OFT's
own `peer` for the source endpoint must name the sending OFT. Each quote also reads
whether the Stellar OFT is paused and how much its inbound rate limit will take
from that chain right now, and declines when it is paused or the amount would not
fit. It declines too when the amount is outside the per-transfer limits the
sending OFT's `quoteOFT` reports.

## Approvals where the OFT locks the token

Where the source OFT locks the token rather than burning it (USDT0 on Ethereum,
whose `approvalRequired()` answers true), the build returns three transactions: an
approve of zero, an approve of exactly the amount, then the send. Tether's USDT
reverts an `approve` that changes one non-zero allowance to another, so a wallet
left with a smaller allowance from an earlier attempt has to clear it first. The
reset carries `skipAlsoWhenExactly: "0"` and the approval carries the amount as
`atLeastBaseUnits`, so a caller that honours both sends the reset only when an
allowance sits between zero and the amount, and neither when it already covers it.

## The delivery fee

LayerZero's fee is paid in the source chain's gas token, on top of the amount. The
quote states the fee `quoteSend` returns. The build prices it again and attaches a
tenth more, in both `fee.nativeFee` and the call's `value` (the OApp requires them
equal). The endpoint reverts a send whose fee rose after it was priced and refunds
anything above the current fee to the sender, so the extra only gets spent if the
fee really did go up. The send's description states the maximum attached.

## The floor is enforced on-chain

Unlike a native mint, the amount received is not equal to the amount sent, because
the token contract can take a fee in transit. The user's minimum is enforced
on-chain through `minAmountLD`, derived from their chosen slippage, so `receivesAtLeast`
is a real floor rather than a copy of `receives`. [Delivery](/developers/concepts/delivery)
covers how a LayerZero arrival is proven.
