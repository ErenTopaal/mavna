# Circle CCTP

`@mavna/adapter-cctp`, id `cctp`, trust model `native-mint`. Circle's Cross-Chain
Transfer Protocol burns USDC on the source chain and mints it on Stellar. Nobody
holds the money in between, and there is no wrapped representation. It carries USDC
only.

```ts
const cctp = new CctpAdapter({ network, rpc, baseReserveStroops });
```

## Chains

CCTP moves USDC from 26 source chains on the test network and 26 on mainnet: 24
EVM chains on each, plus Solana and Starknet on both. Each
chain carries its Circle domain, its `TokenMessengerV2` address, and its USDC
contract. Circle documents BNB Smart Chain as supported, but it is not routable to
Stellar, so it is deliberately absent.

The EVM chain list is generated by a script that verifies every chain on-chain
rather than transcribing an address: for each chain it asks every listed node
for its chain id and refuses the chain if any answers a different one, so the id a
wallet is asked to switch to is the chain's own; then it confirms there is code at
the messenger address, asks that contract for its local minter, asks the minter
which token is local USDC, and asks the token whether it agrees it is USDC with six
decimals. A chain that cannot answer all of these is not in the list. The committed
sweep records no failures. Circle's Stellar-side contracts were confirmed the same
way, by reading the contract instances from the ledger.

## Fees

The bridge fee is read from Circle's live fee service on every quote, so the number
on a route is Circle's current rate rather than a figure this page promises. On the
standard path into Stellar that fee is zero at the time of writing.

## Delivering and proving arrival

The burn's recipient and destination caller are both set to Circle's Stellar
forwarder contract, never the user's address: naming the user directly would mint
to somewhere nothing can move the funds from. The forwarder is validated to be a
real contract before a byte is encoded, and a missing or unverified deployment is
a hard refusal rather than a guess. The ERC-20 approval before a burn is for the
exact amount, never unlimited.

The mint is triggered and paid for by the [sponsor service](/developers/sponsor),
because Circle's forwarder does not serve a Stellar destination that sets a
destination caller, which Stellar requires. [Delivery](/developers/concepts/delivery)
covers how arrival is proven and why a repeat delivery cannot mint twice.
