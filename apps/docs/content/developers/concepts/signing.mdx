# Signing

The SDK builds transactions and hands them back unsigned. You do the signing, and
every payload arrives with a `describes` sentence, written for a person, saying
what signing it does. This page is how the counting works.

## Signatures are told upfront

`Route.signaturesRequired` is the number of times the user will be asked to sign,
stated on the quote before anything moves. It can differ from the number of
transactions `buildTransactions` returns, and that difference is designed: some
transactions are skippable.

`@mavna/routing` plans the steps and counts them. `planTransfer` produces an
ordered list of `PlannedStep`s, each with `needsUserSignature`, and
`signatureCount` counts the ones that do. A `settle-account` step, for instance,
carries `needsUserSignature: false`: the user signs it in advance, and the sponsor
submits it for them, so it is not a prompt at the moment of transfer.

## A transaction can be unnecessary

```ts
interface AllowanceCheck {
  readonly kind: "erc20-allowance";
  readonly token: string;
  readonly spender: string;
  readonly atLeastBaseUnits: string;
}
```

An `UnsignedTransaction` can carry `unnecessaryWhen`. Today its one form is
`erc20-allowance`: the ERC-20 approval before a burn is unnecessary when the
wallet already holds an allowance of at least `atLeastBaseUnits` for `spender` on
`token`. The SDK cannot read the allowance itself, because that needs a
source-chain node the caller holds, so it states the condition and the caller
checks it. `unnecessaryWhen: undefined` means always send it.

## Some transactions need a fresh keypair

`UnsignedTransaction.ephemeralSigners` lists accounts the caller must generate a
fresh keypair for and sign with. It is empty on chains without one, and populated
where a chain requires it: a Solana CCTP burn writes into a new account, so the
adapter names it here. The SDK does not create these. It does not hold keys, ever.

## The Stellar-side signatures the sponsor flow collects

When a transfer creates or opens a brand-new Stellar account, two Stellar
transactions are built in `@mavna/stellar`, both unsigned:

- The **preparation** creates the account and opens the trustline, wrapped in
  sponsorship operations. It is signed by the sponsor and the user; the user
  co-signs the operations that create obligations on their own account, and it
  costs them nothing.
- The **settlement** repays the sponsor's deposit out of the arriving funds. It
  is signed by three parties: the channel account it is sourced on, the user (who
  owns the path payment that spends the arriving value), and the sponsor. It is
  collected before the transfer is sent and held until the money lands.

[Sponsorship](/developers/concepts/sponsorship) is the full lifecycle and the
reason the settlement is signed first.
