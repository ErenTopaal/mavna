# Arriving as another asset

A rail delivers what it carries: CCTP delivers USDC. When a user wants to arrive
holding XLM, or any asset other than the one bridged, a swap leg converts it on
Stellar, and the conversion is one step in the same flow rather than a bridge
followed by a manual trade.

## The venues

`@mavna/swap` puts every venue behind one `SwapProvider` interface: `quote` prices
a conversion and `build` turns that quote into the unsigned transaction that runs
it, from and to the user's own account, with the minimum after slippage as a hard
floor. If the market has moved past that floor the swap fails whole, and the user
keeps the asset that arrived. That is the safe direction to fail. Slippage is
applied by rounding the minimum down with integer math, never through a float.

The swap leg asks every venue that serves the pair at the same time, then reads
the answers in this order and uses the first that is usable and can quote it:

1. **Soroswap**, wherever it serves. It aggregates Soroswap, Phoenix, Aquarius,
   SushiSwap and Comet pools, and Stellar's own orderbook when the money goes to an
   account, and it is the venue that can carry an integrator fee. Its API needs a
   key, which must never reach a browser, so `SoroswapProvider` calls the sponsor
   service's [Soroswap proxy](/developers/sponsor/api#soroswap-proxy) and holds no
   key itself. A sponsor run without a key has no proxy, and the leg moves on.
   Soroswap builds the transaction, so before the user signs it the provider reads
   it back: one operation from the user's account, either aggregator v3's
   `swap_exact_in`, the Soroswap router's `swap_exact_tokens_for_tokens`, or a
   classic strict-send path payment, with exactly the quoted input, the quoted
   tokens at both ends, the user as the one paid, and a minimum no lower than the
   floor the user agreed to. Anything else is refused unsigned.
2. **SushiSwap**, for pairs with USDT0 on mainnet. `SushiSwapProvider` prices by
   simulating Sushi's router over its concentrated-liquidity pools, direct or
   through USDC or XLM, and builds `swap_exact_input_hints` with fresh oracle hints.
   Sushi has no deployment on the test network.
3. **Aquarius**, on both networks. `AquariusProvider` finds a path with Aquarius's
   API and builds `swap_chained` on its router. It routes through Soroban pools, so
   it can deliver to a contract address.

`createSwapVenues` builds that chain for a network, and the chain is itself a
`SwapProvider`: its quote names the venue that gave it, and `build` goes back to
that venue. The order is a preference, not a price race: a later venue that
prices higher still loses to an earlier one that answered. A quote request can
carry an `AbortSignal`. When it fires, the chain stops waiting for the earlier
venues and takes the first quote that has already arrived, in the same order,
and each venue stops its own quote requests.

Stellar's orderbook is not a venue of its own in the chain. It is reached through
Soroswap for account destinations, and `SdexProvider` with `buildPathPayment`
stays exported for anyone who wants the orderbook directly. A classic path payment
cannot deliver to a contract address, so it is never offered for one.

Stellar Broker is not integrated. Its quote endpoint is public, but a swap runs as
a WebSocket session with a partner key in which the server streams transactions for
the client to sign in the background, which is not one conversion the user signs.

`selectSwapProvider` remains for callers that want a single provider for every
pair: the first usable venue in the same order that is not limited to some pairs.

## How it attaches to a route

In `@mavna/routing`, `attachSwapLeg` runs after a rail quotes. It prices the
conversion, rewrites the route's `receives` and `receivesAtLeast` to the wanted
asset, appends a `swap` step, adds its time to the estimate, and adds one to the
signature count, because the user signs the conversion themselves. If no venue
can quote the conversion, the whole route comes back as a `no-liquidity`
rejection that names the wanted asset, rather than a route that cannot complete.
The venues' own reasons are not shown, because they can carry raw node errors.

The rail's quote and its conversion share one budget (`ADAPTER_QUOTE_TIMEOUT_MS`
in a route race). The conversion gets what the rail's quote left of it, and if
nothing has priced it by then the route comes back as `timed-out`, saying the
conversion did not price in time. A route whose rail delivered some other asset
than the one the conversion sells is refused as `asset-unsupported`, and so is a
reserve repaid out of the arrival when the wanted asset is not XLM, because that
repayment is priced in XLM.

When the transfer reaches the swap step, the widget quotes again through the same
chain, builds with the venue that answered, and asks the user to sign.

To the user, "send USDC, receive XLM" is one quote and one flow.
[As a user, arriving as XLM](/guides/receive-xlm) is a single toggle.
