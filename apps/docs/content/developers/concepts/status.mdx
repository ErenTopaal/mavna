# Status and recovery

`@mavna/status` is how a transfer is tracked and recovered. It is a set of pure
functions and a store, not a service: local memory is a convenience, never the
source of truth, and everything must be recoverable from the chain with a lookup
key alone.

## Lookup keys

```ts
type LookupKey =
  | { readonly kind: "source-tx"; readonly value: string }
  | { readonly kind: "deposit-address"; readonly value: string }
  | { readonly kind: "destination-address"; readonly value: string };
```

Any one of the three finds a transfer, which mirrors the three first-class keys on
a `TransferHandle`. Being able to resume from the destination address is the point
prior art misses: most bridges can resume from a transaction hash or a task id and
cannot answer "here is the address I sent to."

`parseLookupKey` takes a pasted string and classifies it. A Stellar address is a
destination and an EVM address (`0x` and exactly 40 hex digits) is a deposit
address. A source transaction is 64 hex digits with or without `0x`, any other
`0x` hex value of up to 64 digits (a Starknet hash shown without its leading
zeros), or a base58 Solana signature of 64 to 88 characters. `toHandle` turns the key into a `TransferHandle`, leaving
`sourceChainId` absent so an adapter that spans many chains searches rather than
declines.

Resumption needs no wallet. Watching a transfer requires no signature, and only
acting on it, such as finishing a delivery, does.

## Slow is not stalled

```ts
type StepPhase =
  | { readonly phase: "idle" }
  | { readonly phase: "blocked"; readonly blocked: Blocked }
  | { readonly phase: "pending"; readonly ref: OnChainRef; readonly expectedByUnix: number }
  | { readonly phase: "stalled"; readonly ref: OnChainRef; readonly overdueSeconds: number; readonly remedy: Remedy }
  | { readonly phase: "done"; readonly ref: OnChainRef; readonly received: Amount }
  | { readonly phase: "refunded"; readonly ref: OnChainRef; readonly to: string; readonly returned: Amount }
  | { readonly phase: "partial"; readonly ref: OnChainRef; readonly received: Amount; readonly expected: Amount; readonly remedy: Remedy }
  | { readonly phase: "failed"; readonly cause: string; readonly remedy: Remedy; readonly ref: OnChainRef | undefined };
```

`pending` and `stalled` both carry an on-chain reference, but they are separate
states so a user can tell "slow but proceeding" from "stalled and needs you"
without reading. `escalateIfOverdue` makes the transition: a `pending` step is
past due once now is later than its start plus its expected duration, and it
becomes `stalled` with the seconds it is overdue and a `Remedy`. Every remedy
carries a `because`, so a failure is never a message with nothing to do beside it.

`refunded` and `partial` are terminal states of their own, not kinds of success,
because a returned transfer rendered as a plain success is a lie about someone's
money.

## The state machine

`applyUpdate` advances a step and refuses to move a finished transfer backwards, so
a late poll cannot walk a delivered payment back to pending: retrying is how one
payment becomes two. `progressOf` reports how far along a transfer is and whether
it needs the user, and `outcomeOf` collapses the steps to one word, with `failed`,
`refunded`, and `partial` taking precedence over `succeeded`. There is no single
"track this" call to make; you assemble tracking from these functions and a store,
which is what lets the same machine drive a live transfer and a resumed one.
