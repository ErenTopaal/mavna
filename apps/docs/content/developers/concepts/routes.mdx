# Routes and rejections

`raceAdapters` from `@mavna/routing` asks every adapter at the same time and
returns a `RouteSet` carrying routes and rejections together:

```ts
import { raceAdapters } from "@mavna/routing";

const routes = await raceAdapters([cctp, axelar, layerzero], request, {
  onUpdate: (partial) => render(partial),
});
```

## Partial results are the normal case

Sources are raced, so some answer before others. `onUpdate` fires each time one
does, with the routes ranked on every publish, because the first route on screen
is the default selection and the default must be the best net outcome even while
slower rails are still answering. `RouteSet.complete` turns true once every source
has answered or timed out. An interface built on this renders results as they land
rather than holding a spinner for the slowest rail.

Each adapter gets `ADAPTER_QUOTE_TIMEOUT_MS`, which is 3000. One slow rail costs
its own route and nothing else.

## A refusal is data

```ts
interface RouteRejection {
  readonly source: string;
  readonly reason:
    | "no-liquidity"
    | "amount-too-small"
    | "amount-too-large"
    | "asset-unsupported"
    | "chain-unsupported"
    | "destination-unsupported"
    | "temporarily-unavailable"
    | "timed-out"
    | "errored";
  readonly explanation: string;
  readonly retryable: boolean;
  readonly detail?: string;
}
```

`detail`, when present, is for whoever runs the integration and never for the
user: a venue's or a node's own words, which can carry raw protocol text or URLs.
Show `explanation`; log `detail`.

A user must be able to see why a route is unavailable rather than watch it quietly
not appear, so a rail that declines, times out, or throws still shows up in
`rejected` with its reason. `explanation` is written for a person: it says what
happened and what to do, and never apologises. Nothing internal reaches it, so a
raw error string or a stack trace never lands in front of a user.

`retryable` is derived from the reason in one place, `rejectionIsRetryable`: a
reason that describes the request (wrong chain, wrong asset, amount out of range)
is settled, and a reason that describes the moment (`temporarily-unavailable`,
`timed-out`, `no-liquidity`, `errored`) is worth asking about again.

## Ranking

```ts
type RouteRanking = "best-received" | "fastest" | "fewest-signatures";
```

The default is `best-received`: the best net outcome after every fee, compared in
integer base units. Pass `ranking` to change it. The comparison never goes through
a floating-point number.

## The circuit breaker

`RaceOptions.breaker` takes a `CircuitBreaker`, which lets an operator take a
source out of rotation without a release. The list is read through a function at
quote time, so changing configuration takes effect on the next quote with no
restart:

```ts
import { createCircuitBreaker, parseDisabledSources } from "@mavna/routing";

const breaker = createCircuitBreaker(() =>
  parseDisabledSources(process.env.MAVNA_DISABLED_SOURCES),
);
```

The format is `id:reason`, comma separated, and the reason is shown to users:
`cctp:Circle is not available right now`. A disabled source produces a rejection
saying exactly that, rather than vanishing, and no in-flight transfer is touched.

## Enrichment

Two transformations run between a rail quoting a route and a user seeing it, both
in `RaceOptions`, both covered on their own pages. `swap` attaches the conversion
into [the asset the user asked for](/developers/concepts/swap), and
`integratorFee` takes [a visible, itemised cut](/widget/configuration) that runs
even at zero basis points, so turning a fee on is configuration rather than a code
path nobody has exercised.
