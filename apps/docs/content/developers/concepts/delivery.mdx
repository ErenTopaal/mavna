# Delivery

A bridge is not done when the source chain confirms; it is done when the value is
on Stellar. Each rail proves arrival its own way, and none of them reads a
recipient's balance and calls it delivered, because that would report money the
user already held as though this transfer brought it.

## CCTP: attestation, then the mint

Circle's attestation service witnesses the burn on the source chain and signs a
receipt that authorises the mint on Stellar. The receipt is public and keyless.

The mint into Stellar has to be triggered by someone on Stellar, because Circle's
own forwarder does not serve a Stellar destination that sets a destination caller,
which Stellar requires. With the [sponsor service](/developers/sponsor) funding
(`MAVNA_RESERVE_FUNDING=sponsor`, what mavna.app runs on the test network), the
sponsor triggers and pays for it. When the sponsor is not funding (`self`), the
receiving account signs and pays `mint_and_forward` from its own XLM, so a Circle
route is offered only to an existing account that can sign for itself and spare
up to 0.1 XLM. Either way the recipient is fixed inside the attested message, so
nobody who triggers it can redirect anything.

A transfer is proven delivered from the delivery itself, never from a balance.
Starting from the burn transaction, Mavna reads the attested message from Circle
and looks on Stellar for the mint that consumed that exact message: the message
transmitter's `message_received` event, emitted with Circle's forwarder as the
caller and this message's nonce as a topic, together with the forwarder's own event
in the same operation, which says how much was forwarded and to whom. Stellar RPC
keeps events for a limited window, so an older delivery is found through Horizon
instead, in the recipient's operations, by the forwarder invocation that carried
this message.

An address alone does not name a transfer. Circle's index is keyed on the burn,
and the forwarder's past deliveries to an address may belong to any transfer at
all, so a lookup by address answers `idle` rather than reporting someone else's
delivery as this one.

An un-indexed burn, or an attested one whose delivery cannot be found yet, stays
`pending`. Neither is reported as `failed`, because reporting failure without
evidence is how a user is talked into sending a second payment.

Delivery is idempotent: Circle's transmitter records a used nonce, so a second
delivery of the same message fails rather than minting twice. That is why
[finishing a delivery yourself](/guides/finish) is always safe.

## Axelar: both legs of the hub route

A transfer through Axelar's Interchain Token Service crosses a hub, so it has two
legs. The first leg reaching "executed" only means it reached the hub. The status
check finds the second leg from the first and requires both delivered before it
reports arrival. It never reads Axelar's `refunded` flag as a returned transfer,
because that flag is leftover gas going home on transfers that delivered perfectly;
there is no field that means the tokens came back, so the adapter never claims they
did.

## LayerZero: the wire amount, not the balance

A LayerZero delivery is proven from the scan indexer's status together with the
amount decoded out of the wire payload, which is the exact figure credited after
fees and dust. The user's minimum-received floor is enforced on-chain through
`minAmountLD`, derived from their chosen slippage, because a token contract can take
a fee in transit and accepting anything back would be an unbounded loss nobody
consented to. An un-indexed message is `pending`, not `failed`.

## LayerZero with a conversion on arrival: the contract's own event

A route that converts on arrival is delivered to the Mavna Arrival Contract, which
swaps on Stellar and sends the wanted asset on. Arrival is proven from LayerZero's
record of the message and the contract's own event, never from a balance. The
message names the contract it was sent to; one that went to another Arrival
Contract is reported as stalled, with the explorer link, rather than as delivered.
For this app's contract, the status reads the event the contract emits for the
message's guid, starting at the delivery's own ledger: `converted` is
`delivered-and-converted`, anything else is `delivered-as-came`.

With no event yet, it reads the endpoint's compose queue for that guid. Nothing
queued is still `pending`; a queued step is `delivered-conversion-pending`, and
the exact queued bytes are rebuilt from LayerZero's record and checked against the
endpoint's hash before they are offered as `finish`, so whoever finishes it can
only run what is waiting. Anyone may finish an overdue step: the contract refuses
any other bytes, and the user's minimum is enforced inside it.

## NEAR Intents: 1Click's own record of the swap

A NEAR Intents transfer is found by its deposit address, or, from the source
transaction, by reading which 1Click deposit address that transaction paid.
1Click's status for that address decides the phase: `SUCCESS` is `done` with the
amount 1Click says settled, or the quote's floor when it does not say, never the
estimate; `REFUNDED` is `refunded` with what came back; `INCOMPLETE_DEPOSIT` is
`stalled`, because the rest must be sent or 1Click returns the deposit once the
quote expires; `FAILED` is `failed` with the deposit address as the reference
1Click's support asks for. A deposit address that is not one of this rail's
transfers answers `idle`.
