# The sponsor service

Two facts force a server into an otherwise client-side product: sponsorship needs
a funded signer, and a funded signer cannot live in a browser. The sponsor service,
in `services/sponsor`, is that signer's home. It is plain Node with no framework,
self-hostable by construction, and running your own with your own key means none of
Mavna's limits are yours.

## Its entire authority

The sponsor signs these kinds of transaction, and each is gated:

1. **Preparations it built itself.** It countersigns and pays for account-setup
   transactions whose source is its own account and whose operations are only
   sponsorship, account creation, and trustline changes. It refuses to submit one
   for any account it holds no signed settlement for: the deposit is a loan, and
   the repayment is signed before the loan is made.
2. **Deliveries whose recipient Circle fixed.** Triggering a mint spends the
   sponsor's fee money, and the recipient is already named inside the attested
   message, so the sponsor cannot redirect anything.
3. **Its half of a settlement.** The spending operation carries the user's own
   signature; the server adds the channel and sponsor signatures at submission
   time, so what it holds in memory can move nothing on its own.
4. **Finishes of a conversion on arrival** (`/compose`, sponsor mode only). It pays
   the fee as the source; a separate executor key signs the one `lz_compose`
   authorization, after the simulation shows nothing nested under it. The fee is
   bounded by any storage renewal due plus 1 XLM.
5. **Its own housekeeping, with nothing a caller chooses in it:** funding its
   settlement channels, creating the executor account with 1 XLM, and the daily
   renewal of the Arrival Contract's storage (sponsor mode only, at most 100 XLM).

In self mode (`MAVNA_RESERVE_FUNDING=self`) it signs none of these that spend: the
accounts pay their own way, and it only builds unsigned trustlines and relays them.

It never holds user funds, never signs a user's transfer, and never sees a user's
key. The gates are enforced in code you can read: operation allowlists per
endpoint, a source check on preparations, and the held-settlement requirement.

## Configuration

Everything is environment variables, read once at start.

| Variable | Required | Default | What it is |
| --- | --- | --- | --- |
| `SPONSOR_SECRET_KEY` | yes | none; the process exits without it | The funded signer's secret. An operational secret: never in the repository, a client bundle, or a log line |
| `MAVNA_NETWORK` | no | `testnet` | `testnet` or `mainnet` |
| `STELLAR_RPC_URL` | no | the foundation's public node on testnet; on mainnet the first of the measured public nodes in `@mavna/stellar` (`PUBLIC_MAINNET_RPC_URLS`) | The Stellar RPC to read and submit through. The foundation runs no mainnet node, so the mainnet default is a third party's; point it at your own provider when you have one |
| `MAVNA_IRIS_URL` | no | Circle's sandbox on testnet, production on mainnet | Circle's attestation service |
| `MAVNA_ALLOWED_ORIGINS` | no | `http://localhost:5173,http://localhost:4319` | Browser origins allowed to call this server, comma separated. Never `*`: this server spends money on request |
| `MAVNA_SETTLE_SWEEP_SECONDS` | no | `120` | How often held settlements are retried without a page asking, for LayerZero and Axelar deliveries whose tab closed. One account at a time, never overlapping. `0` turns it off |
| `MAVNA_RESERVE_FUNDING` | no | `sponsor` | `sponsor`: the sponsor fronts a new account's reserve and is repaid from the arrival. `self`: a temporary switch for running without a funded key; an existing account pays its own trustline reserve, its own Circle delivery on Stellar and any overdue conversion on arrival it finishes, `/deliver` and `/compose` answer `409`, and an address that does not exist yet is declined at quote time. Anything else stops the process at start |
| `MAVNA_STATE_DIR` | no, but set it in production | none: state in memory, lost on restart, with a warning at start | Directory for the caps, held settlements, built transactions, and channel keys and leases, one JSON file each, written atomically. Holds secret channel keys: the process creates it `0700` and its files `0600`; keep it on a private volume. The state records the network it was written for, and the process refuses to start on another network against it: give each network its own directory |
| `MAVNA_CAP_STRANDING_PER_DAY` | no | `75` | Sponsorships that may strand in a day before sponsorship pauses |
| `MAVNA_CAP_VOLUME_EXPENSIVE_PER_DAY` | no | `300` | Sponsorships a day from chains where gas is expensive |
| `MAVNA_CAP_VOLUME_CHEAP_PER_DAY` | no | `200` | Sponsorships a day from chains where gas costs cents |
| `MAVNA_MIN_DELIVERY_USDC` | no | `1` | The smallest Circle mint, in USDC (up to six decimals), the sponsor pays to deliver. `0` delivers any amount |
| `MAVNA_RATE_LIMIT_PER_MINUTE` | no | `120` | Requests per client address per minute, on every endpoint. `0` turns it off |
| `MAVNA_TRUST_PROXY` | no | `false` | `true` behind a reverse proxy: the client address is the last `X-Forwarded-For` entry, the one the proxy appended. This also counts clients for the Soroswap proxy's limits. Set it only when the sponsor's port is reachable from the proxy alone (the compose file binds it to `127.0.0.1`); a port open to the world lets anyone send their own `X-Forwarded-For`. Leave `false` when clients reach the sponsor directly, or anyone can claim any address |
| `MAVNA_CHANNEL_POOL_SIZE` | no | `4` | Settlement channels the sponsor funds for itself, 2 XLM each. One channel carries one settlement in flight; the next is funded only when every one before it is busy. Kept in the state directory with their keys |
| `MAVNA_SETTLEMENTS_PER_CLIENT` | no | `2` | Settlements one client address (counted as the rate limit counts it) may have waiting on a preparation at once. `0` turns it off |
| `SOROSWAP_API_KEY` | no | none; no Soroswap proxy | Soroswap's API key. With it the server proxies Soroswap at `/swap/soroswap/*` so the key never reaches a browser. A secret, like the sponsor key |
| `MAVNA_ARRIVAL_CONTRACT` | no | none; `/compose` answers that it finishes nothing | The Mavna Arrival Contract whose overdue conversions this sponsor finishes. Also kept alive daily (instance and code TTL), paid by the sponsor key. In self mode neither happens, so the sponsor spends nothing, and start-up says so |
| `MAVNA_ARRIVAL_EXECUTOR_SECRET` | with `MAVNA_ARRIVAL_CONTRACT`, in sponsor mode | none; the process exits without it in sponsor mode | A separate key named as the conversion's executor. It signs only `lz_compose` authorizations and holds only its 1 XLM minimum, created by the sponsor on first use. Never the sponsor key: a token named in a message must not reach funded keys |
| `PORT` | no | `8787` | Where to listen |

The curated asset list, the assets this sponsor opens trustlines for, is written
per network in `services/sponsor/src/assets.ts` rather than accepted from the wire:
clients ask by name and the issuer comes from the operator's own list, because a
sponsor that takes issuers from callers pays to phish its own users. It is Circle's
USDC, with the issuers Circle publishes
(`GA5ZSEJYB37JRC5AVCIA5MOP4RHTM335X2KGX3IHOJAPP5RE34K4KZVN` on mainnet), and on
mainnet USDT0 (`GATISXX6BZ6NC7IKQBY37CJD4SOZL3CYZJWXEDG6JVIY4WBS6KXJHN6Q`, the asset
the LayerZero Stellar OFT mints). A sponsor-fronted preparation only ever opens USDC,
the asset its settlement repays; USDT0 is opened only for an account paying its own
reserve.

Every setting is checked at start, and a mistake stops the process with its own
message rather than surfacing later as a refusal nobody can explain.

## Running it

With the app, from a checkout:

```sh
SPONSOR_SECRET_KEY=S... docker compose up
```

Alone:

```sh
pnpm --filter @mavna/sponsor-service build
SPONSOR_SECRET_KEY=S... node services/sponsor/dist/main.mjs
```

`GET /health` answers with the network and the sponsor's public address, which is
the account you fund.

## Capacity and caps

Settlements ride on channel accounts, one in-flight settlement per channel. The
server creates and funds its own channels from the sponsor, one at a time and only
when every channel before it is busy, up to `MAVNA_CHANNEL_POOL_SIZE` (4 by
default). A full pool answers `503`, retryable.

A settlement costs its caller nothing until a preparation backs it, so until then
its channel is held only briefly: five minutes from building it, and five minutes
again from committing it signed. Only the preparation going out holds the channel
to the settlement's own time bound, a day; a preparation the network refuses
outright gives it back to the short hold. One client address may have at most
`MAVNA_SETTLEMENTS_PER_CLIENT` settlements (2 by default) waiting on a preparation
at once, and further asks answer `429`, retryable.

Each settlement's fee is paid by its channel. The sweep tops a channel back up to
2 XLM from the sponsor once it falls below 1.5 XLM, and logs each top-up; a
settlement the network refuses because its channel cannot pay the fee stays held
and is tried again rather than counted as a stranding. `/health` reports
`channels: { size, leased, maxSize }`.

Once an hour the sweep also cross-checks what the sponsor carries: the reserve
slots Horizon says it sponsors against those its own held, prepared settlements
account for, with any sponsored account its records do not know. It is one log
line with the numbers, not a verdict: a stranding stays on the chain's side for good.

Two daily caps bound the money at risk, from the
[sponsorship design](/developers/concepts/sponsorship): a volume cap per source-chain
class (300 a day from chains where gas is expensive, 200 from chains where gas costs
cents and an attack is nearly free) and 75 strandings a day, after which sponsorship
pauses globally for the day. A stranding is a sponsorship whose settlement can never
land: one the network refuses for good, and one whose preparation landed and whose
time bound passed with nothing settled. Cap refusals answer `429` with a user-readable reason.
The counters live behind a storage interface, on disk under `MAVNA_STATE_DIR`
alongside the held settlements and channel keys: a cap that does not survive a
restart is not a cap. Without a state directory they live in memory.

The endpoint-by-endpoint contract is on the [HTTP API](/developers/sponsor/api) page.
