# The sponsor's HTTP API

Every response is JSON. Errors share one shape everywhere, so a caller never parses
two formats:

```json
{ "error": "a sentence written for a person", "retryable": true }
```

`retryable` says whether asking again can change the answer. Nothing internal
reaches the wire: a caller learns that it failed and whether to retry, and the
operator reads the rest from the process log. Browser calls are limited to the
configured origin allowlist.

Every `POST` takes a JSON object of at most 64 KiB. A larger body answers `413`, a
body that is not JSON or not an object answers `400`, and a transaction field that
does not decode as a Stellar transaction answers `400`, all with `retryable: false`.
An unexpected failure inside the server, including a Stellar read that did not
answer, is `500` with `retryable: true`. It may have happened after something was
sent, so it says only that it may not have finished; asking again is safe.

Every endpoint, `/health` included, counts requests per client address over
one-minute windows (`MAVNA_RATE_LIMIT_PER_MINUTE`). Past the limit it answers `429`
with `retryable: true`. Preflight `OPTIONS` requests are not counted.

## `GET /health`

Answers `200` with the network, the sponsor's public address, who pays a new
account's reserve, and the smallest Circle delivery it pays for, in USDC base units
at six decimals, and how many settlement channels it has, how many are in use and
how many it may fund:

```json
{
  "ok": true,
  "network": "testnet",
  "sponsor": "G...",
  "reserveFunding": "sponsor",
  "minDeliveryBaseUnits": "1000000",
  "channels": { "size": 1, "leased": 0, "maxSize": 4 }
}
```

`reserveFunding` is `sponsor` (the sponsor fronts the reserve and is repaid from
the arrival) or `self` (the account pays its own; see below). The widget reads both
fields at quote time, so a route the sponsor cannot carry is declined with the
reason before anyone signs.

## Reserves funded by the account itself

With `MAVNA_RESERVE_FUNDING=self` the sponsor fronts nothing. This is a temporary
switch for running without a funded sponsor key:

- `POST /prepare` for an existing account returns a `changeTrust` whose source is
  the account itself, which signs it and pays its fee and its 0.5 XLM reserve:
  `{ "xdr": "...", "selfFunded": true }`. It answers `400` when the account does
  not exist (an address with nothing in it cannot pay for anything; it needs at
  least 1 XLM to exist and 0.5 XLM more to hold USDC), or when the account cannot
  spare the reserve and the fee above its minimum balance. The daily caps do not
  apply, since no sponsor money is spent. With nothing lent, `assets` may name any
  one curated asset, so an account can open its own USDT0 trustline on mainnet with
  `["USDT0"]`; more than one name answers `400`.
- `POST /submit` submits that transaction exactly as the account signed it. The
  sponsor adds no signature and needs no held settlement.
- `POST /settlement` and `POST /settlement/commit` answer `409`: there is no loan
  to repay.
- The widget does not ask `POST /deliver` for a Circle transfer. The receiving
  account signs and pays Circle's `mint_and_forward` on Stellar itself, built from
  Circle's attestation with the same delivery builder the sponsor uses, so a
  sponsor with no XLM can still serve Circle transfers. A Circle route is declined
  at quote time unless the receiving account is an ordinary `G` account that can
  spare 0.1 XLM for the delivery (plus 0.5 XLM when it opens its USDC trustline
  first), and the connected Stellar wallet must be that account. `POST /deliver`
  answers `409` in this mode, so the sponsor pays for no delivery whoever asks; a
  sponsor-funded deployment still uses it.
- `POST /compose` answers `409` too, and the sponsor does not keep the Arrival
  Contract alive in this mode, so it pays for nothing at all. An overdue conversion on arrival is finished
  from Activity by the receiving account's own wallet, which runs `lz_compose` as
  both the transaction's source and the compose's executor (the call is
  permissionless) and pays its fee from its own XLM. Before asking for the
  signature the widget checks the endpoint holds exactly this message, and that the
  run asks for one authorization only: the wallet's, for `lz_compose` on the
  configured contract with these arguments, with nothing nested under it. It shows
  the fee of the simulated run and asks for the signature only on a second press.
  Most finishes cost a few hundredths of an XLM; one that falls due to renew the
  contract's storage (its instance and code, renewed to 30 days once either has
  less than 15 left) pays that rent, which was 30.7 XLM on testnet for the code
  entry. Compose quotes show that cost, simulated at quote time, in this mode.

## `POST /prepare`

Builds the account-setup transaction for the user to sign. Nothing is spent and
nothing is signed here; the transaction returns unsigned.

Request: `{ "destination": "G...", "assets": ["USDC"], "sourceChainId": "ethereum-sepolia" }`.
`assets` is optional and defaults to `["USDC"]`; each name must be on the operator's
curated list, and since the settlement repays one USDC trustline and nothing else,
the only set accepted is `["USDC"]` (self-funded reserves aside, above). `sourceChainId` feeds the volume cap's chain
class.

Answers:

- `200` `{ "xdr": "...", "sponsor": "G..." }`
- `400` when the destination is missing, is not an address a Stellar account can
  use, can already receive (nothing to prepare), names an asset outside the
  curated list, asks for any set of assets other than `["USDC"]`, or already
  holds USDC (there is no trustline for the sponsor to open). Any field of the
  wrong type is also a `400`
- `429` when a daily cap refuses, with the reason. The caps are checked here,
  before anyone is asked for a signature

## `POST /submit`

Takes back the signed preparation; the sponsor countersigns, pays, and submits.
This is where money moves, so this is where the gates are:

- the transaction must be one this server built and has not countersigned before,
  identified by its hash, and not past its time bound
- it must carry a valid signature from the account being prepared
- a signed settlement must already be held for that account, and the preparation
  must sponsor exactly what that settlement repays: the account itself if the
  settlement revokes the account's sponsorship, and the same set of trustlines
- no other preparation may have been submitted against that settlement
- the daily caps are checked again
- as defence in depth, the source must be the sponsor itself, the operations must
  be only `beginSponsoringFutureReserves`, `endSponsoringFutureReserves`,
  `createAccount`, `changeTrust`, and fee-bump envelopes are refused

Request: `{ "signedXdr": "..." }`.

Answers:

- `200` `{ "txHash": "...", "ledger": 123 }`. A preparation that landed is reported
  as landed even if the cap counter could not be saved afterwards; the operator
  hears about the undercount in the log
- `400` when `signedXdr` is missing or is not a transaction, for a fee bump, a
  source other than the sponsor, an operation outside the list, or a missing or
  invalid signature from the account being prepared
- `409` when the preparation was not built here or has expired ("Ask for a new
  one"), when no settlement is held for the account, when the preparation does
  not match the settlement held for it, or when another preparation has already
  been submitted against that settlement, whether it is still on its way or has
  landed, or when the account opened the USDC trustline itself after the
  preparation was built. One settlement repays one preparation
- `429` when a cap refuses at submission, retryable
- `409`, retryable, with `"prepareAgain": true`, when something else the sponsor
  signed took the preparation's sequence while the user was signing. It can never
  land; ask `/prepare` for a new one and sign that, against the same held
  settlement
- `502` when Stellar would not accept the submission. The preparation is not
  offered again; build a new one

## `POST /settlement`

Builds the settlement for the user to sign: the transaction that repays the deposit
out of the arriving funds, sourced on one of the sponsor's channel accounts. The
path payment buys exactly the XLM the reserve needs and spends at most twice its
value at the live orderbook rate, so the signer's exposure is a number they can
read.

Building takes a channel for one fixed window of ten minutes from the first ask.
Asking again, or committing the signed settlement, returns the same channel and
window and never lengthens it; a built settlement can be committed only within
it, and the sponsor keeps the three latest built for one account. Only a
preparation for the settlement that has landed on-chain holds the channel to the
settlement's own time bound, a day. A settlement never followed by a landed
preparation gives its channel back when the window ends, its held settlement is
dropped with it, and the account waits one more window before it can take
another.

Request: `{ "destination": "G...", "sourceChainId": "ethereum-sepolia" }`.

Answers:

- `200` `{ "xdr": "...", "channel": "G..." }`
- `400` for a missing or unusable destination, one that needs no settling, or an
  account that already holds USDC and has no preparation from this sponsor
- `409`, retryable, while the account's previous settlement is still being
  submitted
- `429` on a cap refusal, or, retryable, when this client address already has as
  many settlements waiting on a preparation as it may, when the account's last
  window lapsed moments ago, or when this address has many builds it has not
  signed
- `503`, retryable, when as many unbacked settlements are out as the sponsor lets
  out at once, when the cap counts cannot be read (sponsorship pauses until they
  are repaired), or when every settlement slot is in use

## `POST /settlement/commit`

Holds what the user signed until their money lands. The server signs nothing here;
what sits in memory can move nothing on its own. Only a settlement this server
built, signed by the account it was built for, is held, and only under that
account. The envelope is also refused unless its operations are only a
strict-receive path payment and sponsorship-revocation operations, and fee bumps
are refused. A new commit replaces a held settlement whose preparation has not
landed yet and is not being submitted.

Request: `{ "destination": "G...", "signedXdr": "..." }`. `destination` is
optional and only checked against the account the settlement was built for.

Answers:

- `200` `{ "held": true }`
- `400` when `signedXdr` is missing or is not a transaction, for a fee bump or an
  operation outside the list, when `destination` names a different account than
  the settlement was built for, or when the account's signature is missing or
  invalid
- `409` when the settlement was not built here or has expired ("Ask for a new
  one"), when the account's preparation has already landed against the
  settlement held for it or is being submitted against it right now, or when the
  settlement's channel slot lapsed or passed to someone else before it was signed

## `POST /settle`

Submits the held settlement for an account, for rails that deliver without this
server: LayerZero and Axelar land funds on Stellar by themselves. It submits only
once the account's preparation has landed and the account can spend what the
trade costs now: Horizon's quote for the settlement's own direct path plus 1%,
never more than the ceiling the account signed, out of USDC not promised to its
own open offers. A quote over that ceiling, or no direct path at all, waits for the
market. Until then it answers that it did not settle and that asking again can. A sweep does the same for every held settlement on an
interval, so a closed tab does not leave the reserve unpaid; see
`MAVNA_SETTLE_SWEEP_SECONDS` in the [configuration](/developers/sponsor#configuration).

Request: `{ "destination": "G..." }`.

Answers:

- `200` `{ "settled": true, "settlementTxHash": "..." }` when it submitted the
  settlement now, or when the settlement already landed, through an earlier call or
  the sweep, within its time bound
- `200` `{ "settled": false, "settlementRetryable": true }` when it is not time
  yet: the preparation has not landed, the money has not arrived, the settlement
  is being submitted right now, or its inclusion was not seen within two minutes.
  Ask again later
- `200` `{ "settled": false, "settlementRetryable": false }` when the settlement can
  never land. It is counted against the stranding cap and no longer held
- `400` when `destination` is not an account or muxed address
- `404` when no settlement is held for the account and none landed recently
- `429`, retryable, when the same account was asked about in the last 30 seconds.
  Only accounts with a held settlement are limited

## `POST /deliver`

Triggers the mint for an attested burn. Idempotent;
[retrying is always safe](/developers/concepts/delivery).

Request: `{ "txHash": "0x...", "domain": 0 }`. Both are required. `txHash` is the
burn's transaction on the source chain: an EVM hash, a Solana signature in base58,
or a Starknet transaction hash. `domain` is Circle's domain for the source chain
and must be one this network routes into Stellar from. Either one malformed answers
`400` before Circle is asked anything.

With `MAVNA_RESERVE_FUNDING=self` it answers `409` with `retryable: false` before
anything else: the receiving account delivers its own transfer, and the sponsor pays
for none.

A delivery costs the sponsor the same whatever it carries, so it pays for none
smaller than `MAVNA_MIN_DELIVERY_USDC`. The minted amount (amount burned less the
fee Circle executed, both read from the attested message) below it, or a message
whose amount cannot be read, answers `400` with `retryable: false`, and nothing is
submitted.

Who the transfer is for is read from Circle's attested message, the one source a
caller cannot choose. A `destination` field is accepted from older clients and
ignored. When the delivery lands, or had already landed, the settlement held for
the recipient Circle attested is submitted in the same breath, and only for a burn
that provably pays that recipient through Circle's forwarder on Stellar.

The server fetches the attestation, simulates the delivery, and signs it only when
the simulated fee is within its inclusion bid plus 1 XLM and it asks for no
authorization. It answers `200` with
one of:

```json
{ "kind": "delivered", "txHash": "...", "ledger": 123 }
{ "kind": "already-delivered" }
{ "kind": "not-attested-yet" }
```

or `404` when Circle has no attested record of the transaction yet (retryable:
nothing is wrong, ask again in a minute; the sponsor also keeps asking by itself,
see below), `502` when Circle's attestation service
could not be reached or did not answer usefully (retryable), `502` (retryable) when
the delivery reached Stellar and failed there, so its fee was paid and nothing was
minted, `503` (retryable) once the sponsor has spent the day's delivery budget
(`MAVNA_DELIVERY_BUDGET_XLM`), or `409` with
`{ "kind": "recipient-not-ready", "detail": "..." }` when the destination cannot
receive yet, which in the designed flow is
[the cue to prepare it](/developers/concepts/sponsorship). When a held settlement is
submitted alongside a delivery, the response carries the settlement's result too,
in the same `settled`, `settlementTxHash` and `settlementRetryable` fields
`/settle` uses.

Every answer to `/deliver` carries `"watching": true` exactly when the burn is on
the sponsor's watch list after the request, and the list is written to disk before
the answer goes out; otherwise there is no `watching` field. A client that sees it
can leave delivering that burn to the sponsor.

A burn asked about before Circle attested it (a `404`, or `not-attested-yet`), or
whose recipient cannot hold USDC yet (`409` `recipient-not-ready`), is also
written down, so a page closed while Circle attests still gets its transfer
delivered. The sweep asks about it again on a backoff (a minute, doubling to half
an hour) and delivers it once attested, through the same checks as this endpoint:
the minimum, the daily delivery budget and the settlement for the attested
recipient. It stops watching a burn once it is delivered or found already
delivered, once it can never be paid for (below the minimum, or an amount that
cannot be read), or two days after it was first asked about; each of those is
logged. One burn is watched once however often it is asked about, and the sponsor
watches at most 8 burns per client address and 1,000 in all; past that the answer
is the same, only nothing is written down. With `MAVNA_RESERVE_FUNDING=self`
nothing is watched.

## Soroswap proxy

Present only when the server holds `SOROSWAP_API_KEY`; without it these paths answer
`404`, and the browser's swap leg moves on to the next venue. The proxy adds the key
on the way to Soroswap and nothing else: the key never appears in an answer, and
Soroswap's own error text is never relayed.

Because every call spends the operator's key, these endpoints are stricter than the
rest. A request whose `Origin` is not on the allowlist answers `403` without reaching
Soroswap. That keeps other web pages off the quota, and nothing more: a client that is
not a browser can send any `Origin` it likes, so it is not access control, and the
limits are what bound the spend. Each client may make 30 calls a minute and all clients together 300; past
either, `429` with `retryable: true`. The client is counted the same way as for
every other endpoint: behind a reverse proxy, set `MAVNA_TRUST_PROXY=true` so it is the
last `X-Forwarded-For` hop.

### `GET /swap/soroswap/health`

Whether Soroswap has indexed markets on this server's network and, on mainnet, its
aggregator is up. Cached for 30 seconds.

```json
{ "network": "mainnet", "usable": true, "protocols": ["soroswap", "aqua", "sushi", "comet", "sdex"] }
```

### `POST /swap/soroswap/quote`

Request:

```json
{
  "network": "mainnet",
  "assetIn": "C...",
  "assetOut": "C...",
  "amount": "100000000",
  "slippageBps": 50,
  "protocols": ["soroswap", "phoenix", "aqua", "sushi", "comet", "sdex"],
  "feeBps": 30
}
```

Assets are contract addresses, the amount is positive integer base units,
`slippageBps` is 0 to 10000, and `network` must be the server's. `feeBps` is
optional and must be 0 or 25 to 300, the range Soroswap accepts. Soroswap records it
but charges the rate in the partner profile behind the key, so it seeds that profile
rather than setting the fee per request.

Answers `200` with Soroswap's quote, checked against the same schema the browser
checks and otherwise passed through unchanged, because it is sent back to build.
`400` when the request fails validation (nothing reached Soroswap), `422` when
Soroswap has no route (`retryable: false`), `429` when Soroswap is busy, `502` when
it could not be reached or answered with something unusable.

### `POST /swap/soroswap/build`

Request: `{ "network": "mainnet", "quote": { ... }, "from": "G...", "to": "G..." }`,
where `quote` is one this endpoint's quote returned. Answers `200`
`{ "xdr": "..." }`, an unsigned transaction for `from` to sign; the browser checks
that its source is the owner before asking for a signature. `409` with
`retryable: true` when Soroswap's fee rate changed since the quote, and the other
statuses as for the quote.

## `POST /compose`

Finishes an overdue conversion on arrival: runs `lz_compose` on the Mavna Arrival
Contract for a message LayerZero has delivered and queued but whose compose step has
not run. Only a sponsor started with `MAVNA_ARRIVAL_CONTRACT` and
`MAVNA_ARRIVAL_EXECUTOR_SECRET` serves it; any other answers `404` with an `error`.

Request: `{ "from": "C...", "guid": "...", "index": 0, "message": "0x..." }`, read
from the delivered message by the SDK (`delivered-conversion-pending` carries it as
`finish`). `from` must be a token the contract accepts. Malformed input answers `400`
before anything is read.

Nothing in the request can change where the money goes. The recipient is inside the
message the user signed on the source chain, and the server checks the message
against the hash LayerZero's endpoint holds for it before submitting; any other
bytes answer `400`. The endpoint runs a queued message once, so a second call
answers `already-composed` and never delivers twice.

The sponsor pays the fee as the transaction's source and names a separate key as
the executor, holding only its 1 XLM minimum (the sponsor creates it with that on
first use). Before that key signs, the simulated run must ask for
exactly one authorization: the executor's, for `lz_compose` on the configured
contract with these arguments, and nothing nested under it. Anything more (a token
in the message trying to spend the executor's authority, for example) is refused
with `400`. The answer is `200` with one of:

```json
{ "kind": "composed", "txHash": "...", "ledger": 123 }
{ "kind": "already-composed" }
```

or `404` with `{ "kind": "not-queued" }` when the endpoint holds nothing for that
message yet, and `429` when the same message was asked about in the last 30
seconds, when one client address has asked for three finishes in the last minute
(counted like every other limit, so behind a proxy it needs `MAVNA_TRUST_PROXY=true`),
or when ten finishes of messages the endpoint really holds have been tried in the last
minute in all (a guid with nothing queued answers `not-queued` and takes no place in
that count). With
`MAVNA_RESERVE_FUNDING=self` it answers `409` before anything else: the account's own
wallet finishes the conversion, and the sponsor pays for none.
