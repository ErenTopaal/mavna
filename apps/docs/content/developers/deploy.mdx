# Deploy to production

Everything a hosted Mavna needs is below, for Mavna's own deployment and for
yours. [Run the whole thing](/developers/install#run-the-whole-thing) covers a
local copy; this page is what changes when real users reach it.

## Build

The workspace needs Node 24.22.0 and pnpm 12.14.0, and refuses any other pnpm
(`devEngines` in package.json), so build in an image that has both. Mavna builds
in `node:24.22.0-slim` with pnpm installed at that version:

```sh
docker run --rm --memory=2500m -v "$PWD":/repo -w /repo \
  -e VITE_MAVNA_SPONSOR_URL -e VITE_MAVNA_NETWORK -e VITE_STELLAR_RPC_URL \
  -e NEXT_PUBLIC_MAVNA_SPONSOR_URL \
  node:24.22.0-slim sh -c "npm i -g pnpm@12.14.0 && \
    pnpm install --frozen-lockfile && \
    pnpm turbo run build --filter=@mavna/app... --filter=@mavna/web... \
      --filter=@mavna/playground... --filter=@mavna/docs... --filter=@mavna/sponsor-service..."
```

Turbo builds the packages first, which the apps and the sponsor import from their
`dist/`. The docs' `next build` is the heaviest step, so the run is capped with
`--memory` and cannot starve its neighbours on a shared host; 2500m is what Mavna's
host uses. The one run gives the landing page and the playground the same testnet
sponsor as the app, which is right for a testnet app. A mainnet app needs a build
of its own: run it again with `--filter=@mavna/app...` alone and the mainnet
variables, and copy `apps/app/dist` to the mainnet app's root before the next
testnet build overwrites it. Run the docs and the
sponsor in the same image they were built in, so the native packages pnpm linked
match.

## The pages

The app, the landing page and the playground are static: serve each one's
`dist/` (`apps/app/dist`, `apps/web/dist`, `apps/playground/dist`) as files, with
any path that is not a file answered by `index.html`, since they route in the
browser. The docs are a Next.js server instead: `next start` on a loopback port,
behind the same proxy (its search index is written into `public/_pagefind` by the
build and served from there).

Each page inlines the sponsor it calls at build time, and a production build stops
with the variable's name when it is missing, so a hosted page can never quietly
call `http://localhost:8787`, which no visitor can reach.

| Page | Variable | Mavna's testnet value |
| --- | --- | --- |
| App (`mavna.app`) | `VITE_MAVNA_SPONSOR_URL` | `https://sponsor.mavna.app` |
| App | `VITE_MAVNA_NETWORK` | `testnet` |
| App | `VITE_STELLAR_RPC_URL` | empty: the public testnet node |
| Landing (`web.mavna.app`) | `VITE_MAVNA_SPONSOR_URL` | `https://sponsor.mavna.app` |
| Playground (`playground.mavna.app`) | `VITE_MAVNA_SPONSOR_URL` | `https://sponsor.mavna.app` |
| Docs (`docs.mavna.app`) | `NEXT_PUBLIC_MAVNA_SPONSOR_URL` | `https://sponsor.mavna.app` |

The landing page, the playground and the docs run their widgets on testnet, so
their sponsor is always a testnet one.

For mainnet the app needs its own sponsor, since a sponsor serves one network:
`VITE_MAVNA_NETWORK=mainnet`, `VITE_MAVNA_SPONSOR_URL` naming the mainnet sponsor,
and `VITE_STELLAR_RPC_URL` naming your own Stellar RPC provider (the foundation
runs no public mainnet node). To offer both networks behind the header toggle, set
`VITE_MAVNA_NETWORKS=testnet,mainnet` with `VITE_MAVNA_TESTNET_SPONSOR_URL` and
`VITE_MAVNA_MAINNET_SPONSOR_URL`; the build refuses a listed network without one.

## The sponsor

One sponsor per network, each its own process, key, state directory and hostname.

| Variable | Testnet (`sponsor.mavna.app`) | Mainnet |
| --- | --- | --- |
| `MAVNA_NETWORK` | `testnet` | `mainnet` |
| `SPONSOR_SECRET_KEY` | the testnet sponsor key | its own key, never the testnet one |
| `STELLAR_RPC_URL` | empty: the public testnet node | your own provider |
| `MAVNA_RESERVE_FUNDING` | `sponsor` | `self` |
| `MAVNA_PRODUCTION` | `true` | implied by `mainnet` |
| `MAVNA_STATE_DIR` | a persistent private volume, e.g. `/var/lib/mavna` | a different persistent private volume |
| `MAVNA_TRUST_PROXY` | `true` | `true` |
| `MAVNA_ALLOWED_ORIGINS` | `https://mavna.app,https://www.mavna.app,https://web.mavna.app,https://playground.mavna.app,https://docs.mavna.app` | the app's origins only |
| `SOROSWAP_API_KEY` | set | set |
| `MAVNA_PROVISIONAL_SETTLEMENTS` | the default, 16, unless many users start at once | not used in `self` mode |
| `MAVNA_CHANNEL_FLOOR` | the default, 4: idle channels above it go back to the sponsor after a day | not used in `self` mode |
| `MAVNA_ARRIVAL_CONTRACT` | `CBBT5762DOTXQMDPWSCMPSKB6YMXHS3XJJO7R3DZPXVHK62TOC5HV7XQ` | none: no mainnet deployment yet |
| `MAVNA_ARRIVAL_EXECUTOR_SECRET` | a separate executor key | none |

Why each one matters:

- **`MAVNA_STATE_DIR` is not optional in production.** A mainnet sponsor, or one
  started with `MAVNA_PRODUCTION=true`, refuses to start without it. Without it the caps, held
  settlements, built preparations and channel keys live in memory, and every
  restart (a crash, a reboot, a redeploy) drops them: XLM funded into a channel
  becomes unreachable, a reserve fronted for a settlement that was waiting on
  delivery is never repaid, and the daily caps start again from zero. Mount it on
  a volume that outlives the container, readable only by the sponsor; the process
  creates it `0700`. Each network gets its own directory.
- **`MAVNA_TRUST_PROXY=true`, with the port bound to loopback.** Behind a reverse
  proxy every request otherwise arrives from the proxy's address, so all users
  share one rate limit and one client could exhaust it for everyone. It is safe
  only when the proxy is the one way in: publish the port on `127.0.0.1` only and
  let the proxy, which appends the client to `X-Forwarded-For`, face the internet.
- **`MAVNA_RESERVE_FUNDING`.** Testnet runs `sponsor`: the sponsor fronts new
  accounts' reserves and pays Circle's deliveries on Stellar. Mainnet runs `self`:
  the sponsor spends nothing, new addresses are declined, and the receiving account
  pays its own trustline and delivery.
- **`MAVNA_ALLOWED_ORIGINS`** must list every page whose widget calls this sponsor,
  the docs included. A page left out gets its Circle routes declined as
  unreachable.
- **`SOROSWAP_API_KEY`** keeps the Soroswap venue in the conversion leg. The key
  stays on the server; without it, conversions use SushiSwap and Aquarius only.
- **`MAVNA_PROVISIONAL_SETTLEMENTS`.** One channel carries one new-account
  settlement in flight. The sponsor funds channels as they are needed, 2 XLM each,
  up to twice the smaller daily volume cap plus this many, so the pool cannot run
  out within the caps. `MAVNA_CHANNEL_POOL_SIZE` is no longer read; the sponsor
  says so at start if it is still set.
- **The Arrival Contract** pair lets the testnet sponsor finish overdue
  conversions on arrival and keep the contract alive. Mainnet has no contract
  until it is independently audited.

## Running it

The sponsor listens on 8787 inside its container. Publish it on a free loopback
port of the host and point the proxy at that same port. Mavna's host already has
8787 taken by another service, so it publishes the sponsor on 3007; the docs'
`next start` listens on 3000 inside its container and is published on 3100:

```sh
docker run -d --restart unless-stopped --name mavna-sponsor \
  --env-file sponsor.env \
  -v mavna-sponsor-state:/var/lib/mavna \
  -p 127.0.0.1:3007:8787 \
  -v "$PWD":/repo -w /repo node:24.22.0-slim \
  node services/sponsor/dist/main.mjs

docker run -d --restart unless-stopped --name mavna-docs \
  -p 127.0.0.1:3100:3000 \
  -v "$PWD":/repo -w /repo/apps/docs node:24.22.0-slim \
  node_modules/.bin/next start --port 3000
```

`sponsor.env` holds the variables above and is readable only by its owner. The
proxy in front, for example Caddy, which discards any `X-Forwarded-For` a client
sends and sets its own. The ports in it are the host ports published above:

```
sponsor.mavna.app {
  reverse_proxy 127.0.0.1:3007
}

docs.mavna.app {
  reverse_proxy 127.0.0.1:3100
}

mavna.app, www.mavna.app {
  root * /var/www/mavna-app
  try_files {path} /index.html
  file_server
}

web.mavna.app {
  root * /var/www/mavna-web
  try_files {path} /index.html
  file_server
}

playground.mavna.app {
  root * /var/www/mavna-playground
  try_files {path} /index.html
  file_server
}
```

Copy each page's `dist/` to its root after a build.

## Check it once it is up

- The start-up log has no line saying `MAVNA_STATE_DIR is not set`.
- `curl https://sponsor.mavna.app/health` names the network and the reserve
  funding you meant: `"network":"testnet"` and `"reserveFunding":"sponsor"` here,
  `mainnet` and `self` on the mainnet sponsor.
- After a restart the log still has no such line, and `ls` on the volume shows the
  state files the sponsor wrote.
- Open each page, pick a Circle route with a real address, and see it quote. A
  page built without its sponsor never gets this far: its build stopped.
