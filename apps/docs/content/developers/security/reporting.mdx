# Reporting a vulnerability

This software moves other people's money across systems where most mistakes cannot be
undone. It will have vulnerabilities, and the useful thing is to be told about them
before anyone else is.

## Report it privately

Email **security@mavna.app**. Do not open a public issue, and do not post it
anywhere else first.

Useful to include, in whatever detail you have:

- What an attacker gets, and what they need in order to get it.
- The package and, if you have it, the commit or file.
- Whether it is reachable from the widget, since that one runs in other people's pages
  and a compromise there harms every wallet that embedded it.
- Anything that reproduces it. A failing test is the best possible report.

## What is in scope

Everything, with one emphasis. The [security model](/developers/security/model) claims
the product is non-custodial: the SDK builds transactions and returns them unsigned,
nothing signs on a user's behalf, and no transfer routes through an account Mavna
controls except the bounded sponsor. If you find something that contradicts that, it
is the most serious report you could send.

Outages of the bridges, routers, and RPC providers in the path are their incidents
rather than vulnerabilities here; every deployment can
[stop routing through a degraded provider](/developers/concepts/routes) without waiting
for a release. The paths this project most wants to hear about are the ones where a
wrong value destroys funds permanently: cross-chain address encoding, recipient
encoding in CCTP hook data, and anything that decides what a destination is from the
shape of its string.
