# Security model

This software moves other people's money across systems where most mistakes cannot
be undone: no support desk that reverses a transfer, no chargeback, no
administrative key. The properties below follow from that fact, and each is meant to
be verifiable by reading the code rather than trusting the paragraph.

## Non-custodial by construction

The SDK builds transactions and returns them unsigned. Signing and submission belong
to the caller's wallet; the SDK never holds, generates, transmits, or logs a key, and
no transfer routes through an account Mavna controls. Destination addresses are the
user's, always.

The one controlled account is the sponsor, and its existence is bounded rather than
assumed safe: its [entire authority is five kinds of transaction](/developers/sponsor), each gated
in code, its exposure is capped daily, and its key is an operational secret that
lives only in the environment of one self-hostable process.

## The unrecoverable paths get unusual treatment

A few code paths can permanently destroy funds; CCTP's hook encoding is the clearest,
where the mint recipient, the destination caller, and the recipient encoding in the
hook data all must be exactly right. Those paths validate before they construct
anything and fail loudly rather than producing a plausible-looking wrong transaction.
A route carries its own destination, so a quote cannot be signed against an address
other than the one it was quoted for.

Address handling follows the same rule. Stellar has several address forms with
different behaviour, and the SDK classifies what a destination actually is rather than
inferring it from the shape of the string. Handing a secret key where an address
belongs is refused outright.

## Remote answers are input, not truth

Quotes, fee estimates, token lists, and status responses arrive from remote services
and then drive money movement, so they are validated before they influence a
transaction, and the failure modes that make no sound get named guards: Axelar's fee
estimator returning zero for an unknown chain, LayerZero's registry serving a
superseded endpoint that still answers, a Stellar node answering from behind the
ledger it already showed. Where a value can move between the quote and settlement, the
user's exposure is bounded by a number they chose.

## Asset identity and curation

Anyone can issue a Stellar asset called USDC. Identity is code plus issuer everywhere
a decision is made, and wherever the product presents a list,
[someone named curates it](/developers/concepts/model). The sponsor opens trustlines
only for assets on its operator's own list, by name.

## What a user signs

A signature is consent. Every payload carries a sentence saying what signing it does,
approvals ask for the exact amount rather than unlimited authority, signature counts
are told upfront, and the sponsor simulates every delivery before it submits one.

## Failing safely

Every failure mode in the transfer design leaves funds where the user can get them: an
undelivered mint stays deliverable, a failed conversion leaves the arrived USDC in the
user's account, and a failed settlement leaves everything that arrived with the user
and costs the sponsor instead. Resumption needs only what the user already has, and
retrying a delivery [cannot double-mint](/developers/concepts/delivery). Where
something cannot be completed, it says so plainly, because ambiguity leads users to
retry, and retrying is how single failures become double payments.

## Third parties can be turned off

A dependency on a bridge or provider is a dependency on their incidents. The
[circuit breaker](/developers/concepts/routes) stops routing through a named source
without a release, shows users the operator's reason, and never touches a transfer
already in flight.

## The widget's supply chain

The widget runs in other people's pages, so a compromised release would harm every
wallet that embedded it. Its dependency discipline reflects that. React and React-DOM
are its only peers; every dependency is pinned to an exact version behind a lockfile;
a new release soaks for a day before the workspace will install it; exotic
sub-dependencies are blocked; and install scripts run only for packages allowlisted by
name, so anything else fails the install rather than executing quietly. What the
widget will not do to a host page is [stated in its own docs](/widget).

Found something that contradicts any of this? That is the most serious report you
could send: [report it privately](/developers/security/reporting).
